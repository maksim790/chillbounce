## Цель и запрос

Подготовить локальный Git-репозиторий Chillbounce для работы по согласованной схеме main → dev → feature-ветки. Пользователь вызвал prepare-task с запросом «инициализируй git репозиторий». В рамках подготовки создаётся только тикет; выполнение передаётся start-task.

## Основания

- [AGENTS.md](../../AGENTS.md#repository-branches): main — production-ветка, dev — интеграционная. Пользователь уточнил исключение для первоначальной настройки: первый коммит в main, затем создание dev от него; дальнейшая разработка — в feature-ветках от dev.
- [Home](../Home.md), [состояние системы](../02-System/Overview.md), [политика проверок](../05-Engineering/Testing-Strategy.md).
- При подготовке `git status --short` сообщил, что текущий каталог не является репозиторием; `git --version` вернул `2.33.0.windows.2`. В корне обнаружены только AGENTS.md и docs; все существующие документы нужно сохранить.
- Документация Git получена через Context7 `/git/htmldocs`: [git init](https://git-scm.com/docs/git-init), [unborn branch](https://git-scm.com/docs/gitglossary#def_unborn). Инициализация без первого коммита ещё не даёт общей истории для двух обычных веток.

## Предлагаемый объём и границы

Инициализировать локальный репозиторий в корне Chillbounce с веткой main. Сделать первый содержательный коммит проверенной существующей документации в main, затем создать dev от этого коммита и переключиться на dev. Это согласованное пользователем разовое исключение для первоначальной настройки. Отдельная начальная ветка не нужна; дальнейшие задачи выполняются в feature-ветках от dev.

Первый коммит включает существующие AGENTS.md и docs, в том числе этот тикет и необходимые обновления сведений о состоянии Git и навигации по задачам. Перед staging повторно проверить инвентарь и diff: новые посторонние файлы не включать автоматически. Коммит: короткий conventional subject, например `chore: initialize repository`, с кратким описанием состава начальной истории.

Уточнение при выполнении: пользователь ранее выбрал создание README до Git; завершённые README.md и связанная навигация также включаются в первый коммит как существующая документация. Исходный объём сохранения документов не меняется.

Remote, GitHub-репозиторий, push, PR, настройка серверной защиты веток и деплой в объём не входят. Не менять глобальную конфигурацию Git. Использовать существующую идентичность автора; если она отсутствует, запросить имя/email, не придумывая их. Исходники приложения и зависимости не добавлять. Существующие файлы сохраняются.

## Критерии приёмки

1. Корень локального репозитория совпадает с корнем Chillbounce; существующие файлы сохранены.
2. Есть первый содержательный коммит проверенной проектной документации в main. main и dev указывают на этот коммит, текущая ветка — dev.
3. Однократное исключение для первого коммита в main зафиксировано в AGENTS.md; дальнейшие задачи следуют обычной схеме feature-веток от dev. Отдельная начальная ветка не создаётся.
4. После коммита рабочее дерево чистое в части задачи; обнаруженные посторонние изменения сохранены и явно перечислены, если появятся.
5. Vault отражает выполненную инициализацию, наличие первого тикета и фактические проверки. Markdown-ссылки разрешаются.
6. Remote не добавлен, публикация не выполнялась, глобальные настройки не изменены. Если репозиторий уже появился к началу выполнения или Git не может создать коммит, не переинициализировать и не выдумывать результат: проверить состояние и сообщить препятствие.

## Проверка при выполнении — запланировано

- До изменений: повторный осмотр файлов, `git status --short`, проверка доступности идентичности автора без чтения произвольной конфигурации или секретов.
- После настройки: `git rev-parse --show-toplevel`, `git branch --show-current` (ожидается dev), `git branch --list`, `git log -1 --format=%s`, сравнение `git rev-parse main dev`, `git status --short`, `git remote`.
- Перед коммитом: просмотр staging diff и списка файлов; обязательные проверки [DoD](../05-Engineering/Testing-Strategy.md). После коммита — проверка дерева и состава коммита.
- Проверка ссылок через read-only validator, указанный в политике проверок. Проверки приложения неприменимы: код и зависимости этой задачей не создаются.

При подготовке выполнены только осмотр и проверка доступности Git; перечисленные проверки результата инициализации ещё не выполнялись. Команды проверки опираются на Git CLI; синтаксис доступной версии повторно проверить при выполнении при необходимости.
