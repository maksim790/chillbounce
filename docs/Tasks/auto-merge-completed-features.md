# Коммиты по ходу тикетов, merge и push завершённой задачи

Created: 2026-11-12T12:59:03Z
Status: ready

## Цель и запрос

Исходный запрос — локальный merge завершённой feature-ветки в dev. Последующие уточнения пользователя расширили порядок: коммиты по ходу выполнения тикета; после самостоятельного тикета либо всей группы одной задачи — merge в dev, проверка и push dev. PR и push не предлагаем как варианты; push выполняется стандартно, PR — только по явному запросу. Пользователь утвердил этот порядок и поручил выполнить задачу.

## Источники и противоречия

- До выполнения [AGENTS.md](../../AGENTS.md#task-completion-and-integration) требовал ждать выбора из трёх вариантов перед merge, push или PR. Это конфликтовало с новым запросом и заменяется согласованно, а не дополняется противоречащим пунктом.
- [Политика проверок](../05-Engineering/Testing-Strategy.md#коммиты-и-интеграция) также синхронизируется с новым порядком.
- Навигация vault: [Home](../Home.md); учёт источников: [Index](../06-Sources/Index.md).
- При подготовке рабочее дерево было чистым, активна dev. Для задачи создана `feature/auto-merge-completed-features` от dev. При запуске выполнения в ней присутствовал только этот незакоммиченный тикет. К этому моменту пользователь настроил origin; fetch обнаружил origin/main, remote dev ещё отсутствовала.

## Объём и критерии приёмки

1. AGENTS.md явно задаёт стандартный порядок: проверять и коммитить законченные логические части по ходу тикета; после полного завершения самостоятельного тикета — проверить состав ветки, локально объединить feature-ветку с dev, проверить результат и выполнить обычный push dev без повторного подтверждения. Для группы тикетов одной задачи используется общая feature-ветка; merge и push выполняются после всех согласованных дочерних тикетов и общих критериев интеграции, а не после каждого ребёнка. Промежуточные коммиты не запускают интеграцию. Явные указания пользователя имеют приоритет.
2. Обязательное меню из трёх вариантов и требование ждать отдельного выбора перед стандартным merge/push заменены кратким отчётом. Агент не предлагает push или создание PR. Push dev разрешён стандартным порядком; PR создаётся только по явному запросу. Анализ без изменений и первоначальная настройка не запускают автоматическую публикацию.
3. Сохранены проверки актуальности dev, fetch при наличии remote, fast-forward-only обновление dev от соответствующей remote-ветки, проверка посторонних изменений, защита dirty-файлов и согласование неоднозначных конфликтов. Обязательные проверки с ошибкой блокируют стандартный merge. Недоступные проверки явно отражаются с причиной и ограничениями по действующей политике; отсутствие проверки не выдаётся за успех.
4. После любого merge проверяется итоговое состояние до push. При неудаче агент сообщает проблему, не публикует результат и не выполняет разрушительный откат автоматически. При отсутствующем/неоднозначном remote, расхождении веток, отклонении push или невозможности безопасной интеграции сохраняет работу и сообщает препятствие; не утверждает, что задача опубликована. При определённом origin и целевой dev обычный push может создать отсутствующую remote dev.
5. В обычном успешном случае работа заканчивается на dev. Feature-ветка сохраняется: её удаление, force push и перенос в main по-прежнему требуют отдельного явного разрешения. Исключения для первоначальной настройки и анализа без изменений сохранены.
6. Политика проверок синхронизирована с новым порядком, карта источников отражает новое решение, Home содержит ссылку на этот тикет. Исторические записи в завершённых тикетах не переписываются. Markdown-ссылки разрешаются; отсутствуют противоречащие указания об отдельном выборе перед стандартным merge/push.

## Границы

Это изменение инструкций рабочего процесса, без кода приложения, CI-автоматизации, серверных настроек или Git hooks. Отдельные архитектурный дизайн и implementation plan не требуются. Merge-стратегия не предписывается; squash/rebase не выполняются автоматически ради этой задачи. Подготовка сама по себе не разрешала публикацию; последующее утверждение пользователем и поручение выполнить задачу разрешают согласованные коммиты, merge и push dev, включая завершение этой задачи. Remote не создаётся и не меняется.

## План проверки — запланировано

- Саморевью всех затронутых разделов AGENTS.md и политики проверок по критериям 1–6; проверить успешный сценарий, проваленную/недоступную проверку, конфликты, постороннюю работу и явное указание пользователя использовать PR.
- Read-only validator vault по команде из политики проверок; отдельно проверить локальные ссылки AGENTS.md, поскольку validator обходит docs.

- Не выполнять пробные merge, push или создание PR ради проверки текстового правила. При завершении самой задачи выполнить согласованные локальную интеграцию, проверки и обычный push dev; проверить фактический результат.
