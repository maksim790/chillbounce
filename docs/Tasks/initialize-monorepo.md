## Объём и ограничения

Включены root tooling, apps/ и packages/, root scripts, документация и проверки пустого workspace. Будущая структура: apps/shell, wallet, crypto, admin (React host/remotes), api (NestJS), worker (фоновые задачи); packages/ui, contracts, config. Эти дочерние пакеты сейчас не создавать. Worker не трактовать как уже выбранную модель развёртывания backend.

Не создавать Git-репозиторий, приложения, generators, фиктивные исходники/тесты, Nx или Nx Cloud, React/NestJS/Vite/Module Federation зависимости или дополнительные инструменты без необходимости. Не перезаписывать существующие файлы без анализа. Секреты не читать и не сохранять.

**История исключения процесса:** исходный запрос запрещал Git-коммиты, поэтому первоначальное локальное выполнение завершилось без коммитов и интеграции. 2026-11-12 пользователь отменил это ограничение: «коммить по правилам тикета измения и делай что надо — строка была ошибкой». Актуальный порядок — коммит проверенного результата, локальный merge в dev, повторная проверка и обычный push origin/dev согласно AGENTS.md. PR не требуется; main и удаление веток не входят в разрешённый объём.

## Критерии приёмки

1. Корневой package.json имеет private: true и packageManager с точной актуальной стабильной версией pnpm, проверенной на момент реализации. Версии TypeScript, ESLint, typescript-eslint, Prettier и совместимых вспомогательных пакетов проверены по registry и официальным требованиям; prerelease не используются. Совместимый Node.js и основания выбора версий документированы. Если latest несовместимы, конфликт явно разрешён до объявления готовности.
2. pnpm-workspace.yaml включает apps/* и packages/*; директории существуют и сохраняются при checkout (допустимы .gitkeep). Используется один корневой pnpm-lock.yaml, без конкурирующих lockfiles. pnpm install проходит, повторная установка с frozen lockfile не меняет lockfile.
3. Workspace управляется pnpm без Nx, nx.json, облачной интеграции и замещающего task runner. Для будущих frontend/backend пакетов предусмотрен запуск их package scripts средствами pnpm. Кеширование результатов задач не входит в объём. Приложений и generators нет.
4. tsconfig.base.json включает strict: true и только общие compiler options. Нет глобальных JSX/DOM, Node types, decorators, frontend moduleResolution либо иных настроек, навязывающих один runtime. Приложения смогут расширять базу; root typecheck корректно завершается без проектов и не вызывает ошибку отсутствия входных файлов. Этот результат означает отсутствие целей, а не проверку будущего кода.
5. eslint.config.mjs использует Flat Config, рекомендованные @eslint/js и typescript-eslint правила. Генерируемые файлы, зависимости и кеши исключены. Конфигурация допускает будущие React/NestJS расширения без установки этих зависимостей сейчас. Линт проверяет существующие подходящие конфигурационные файлы и не скрывает реальные ошибки глобальным подавлением правил.
6. Есть единая конфигурация Prettier и .prettierignore. Форматирующие правила ESLint не конфликтуют с Prettier; eslint-config-prettier допустим, дополнительные format-плагины без необходимости не добавляются. Существующие документы не исключаются целиком только ради зелёной проверки; необходимые изменения форматирования сохраняют содержание.
7. .gitignore исключает node_modules, dist/build/coverage, Vite cache, .env и локальные варианты окружения, логи, временные, IDE/OS файлы. .env.example, конфигурации и pnpm-lock.yaml остаются доступными Git. Существующие правила, если появятся до реализации, сохраняются после анализа.
8. Root scripts lint, lint:fix, format, format:check и typecheck работают в текущем workspace без приложений. lint:fix и format повторяемы; последующие lint и format:check проходят. Root typecheck запускает имеющиеся package scripts через pnpm, допускает отсутствие целей и не включает себя в рекурсию. Пропуск отсутствующего script не скрывает ошибку существующего script. Нет фиктивных success-заглушек вместо проверок.
9. README, AGENTS.md и затронутые страницы vault отражают фактические команды и проверенные результаты. Система, решения, roadmap, открытые вопросы и карта источников актуализированы там, где запрос закрывает прежнюю неопределённость; будущая архитектура не названа реализованной. Локальные Markdown-ссылки разрешаются.
10. Итоговый diff соответствует только инфраструктуре и её документации; приложения и финансовая/блокчейн логика отсутствуют. Отчёт перечисляет проверки, ограничения пустого workspace и фактические результаты коммитов, интеграции и push dev. Изменение этого процессного критерия прямо разрешено отменой ошибочного запрета пользователем.
