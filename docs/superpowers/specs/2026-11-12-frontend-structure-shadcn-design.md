Статус: дизайн v3 согласован целиком вместе с планом v2 ответом пользователя «Подтвердить план»; запись согласования 2026-11-12T17:38:29Z. Заменяет несогласованные v1/v2 после исследования внешних примеров: пользователь поручил сгруппировать frontend в apps/frontend рядом с apps/api и показать обновлённый план. ## Цель, основания и подход

Общий стандарт организации Shell и всех remotes для последующих задач. Сохраняются [согласованные обязанности](../../02-System/Frontend.md#будущие-обязанности) и текущая техническая federation-связка. Пользователь явно выбрал shadcn/ui, затем ответил «давай» на предложение структуры по сценариям, общего UI-пакета и документационного этапа. Позже пользователь предложил apps/frontend и apps/api и поручил переделать план. Разделение расположения исходников и их runtime-доставки разъяснено; UI через Shell не считается выбранным решением. Полный дизайн v3 подтверждён при финальном review вместе с планом v2.

Рассмотрены два подхода: структура по сценариям app/pages/features/shared и полный Feature-Sliced Design с entities/widgets. Выбран первый: меньше обязательных слоёв при текущем размере проекта; цена — границы сценариев надо соблюдать явно, без опоры на полный набор правил FSD. Этот стандарт не называется полной реализацией FSD.

## Целевая структура monorepo

```text
apps/
├── frontend/
│   ├── shell/
│   ├── wallet/
│   ├── admin/           # Будущий remote мониторинга
│   └── packages/
│       └── ui/          # Общие исходники shadcn/ui и стили
└── api/                 # Будущий NestJS backend

package.json
pnpm-workspace.yaml
pnpm-lock.yaml
tsconfig.base.json
```

Frontend-приложения и их общие пакеты группируются внутри apps/frontend; apps/api — одно будущее backend-приложение, не контейнер frontend-модулей. Плата за группировку — более длинные пути; преимущество — явное расположение frontend-кода и UI отдельно от backend. Первоначальное плоское размещение apps/shell, apps/wallet и корневого packages/ui заменяется этой целевой схемой, но текущие исходники не перемещаются в документационной задаче. История прежних решений сохраняется.

Корневые package.json, pnpm-workspace.yaml, pnpm-lock.yaml, нейтральный TS base и общие ESLint/Prettier остаются едиными. apps/frontend — каталог группировки, которому не нужен фиктивный package.json. Существующий корневой packages не удаляется; будущие cross-platform контракты обсуждаются отдельно. Worker и crypto этой задачей не создаются и нового назначения не получают.

## Структура каждого приложения

```text
apps/frontend/<shell-or-remote>/src/
├── app/               # Композиция: App, providers, router, интеграции
├── pages/             # Страницы, собирающие сценарии
├── features/          # Отдельные пользовательские сценарии
├── shared/            # Общий код только этого приложения
│   ├── api/           # Транспорт и общая инфраструктура запросов
│   ├── lib/           # Локальные независимые утилиты
│   └── ui/            # Локальные визуальные композиции без бизнес-логики
├── main.tsx
└── bootstrap.tsx

apps/frontend/packages/ui/src/
├── components/        # Общие shadcn/ui-компоненты и визуальные примитивы
├── hooks/             # Только общие UI-хуки
├── lib/               # Только утилиты UI
└── styles/            # Общая тема и токены
```

Папки создаются при появлении реального содержимого. Примеры сценариев — login в Shell, internal-transfer в Wallet; примеры не разрешают их реализацию. Внутри features/<scenario> код UI, состояния, запросов, типов и валидации располагается рядом; внутренние подпапки добавляются по размеру, обязательного шаблона для каждой feature нет. Специфичные endpoint-функции принадлежат сценарию, shared/api не становится складом бизнес-запросов. Дополнительный app-specific shared/hooks вводится только при фактическом повторном использовании.

## Импорты и публичные границы

- Направление: app → pages → features → shared → apps/frontend/packages/ui; верхний уровень может использовать нижние напрямую. Обратные зависимости запрещены. pages не импортируют другие pages, features — внутренности других features; композиция сценариев делается выше.
- Внутри одной feature допустимы прямые относительные импорты. Для внешнего использования определяются узкие точки входа; обязательного index.ts нет. Допустимы прямые импорты из предназначенных для внешнего использования модулей. Не создавать общий barrel, экспортирующий всё приложение. Страница не обязательна, если компонент непосредственно собирается app.
- Между приложениями нет импортов исходников и path aliases в соседний app. Shell использует публичный federation-модуль remote. Текущий wallet/Wallet без props и bootstrap с отдельным React root сохраняются; exposed-компонент не создаёт root и не становится частью Shell layout.
- apps/frontend/packages/ui не зависит от Shell, remotes или backend и не содержит auth, балансы, API или бизнес-состояние. Общие элементы берутся из него, а не копируются в каждый remote. Пакет подключается как workspace-зависимость через объявленные package exports; конкретные aliases и exports согласуются при внедрении, а не добавляются этим документом.
- Не вводить shared business package, store, router или новую federation-sharing политику без отдельной потребности. Сохраняется текущий React singleton; общий исходный UI-пакет не означает отдельный remote или автоматически единую runtime-копию.
- Папки сценариев/страниц — kebab-case, файлы React-компонентов — PascalCase.tsx, хуки — useName.ts, обычные модули — kebab-case.ts. main.tsx/bootstrap.tsx сохраняют свои роли; env declarations остаются техническими файлами приложения. Конкретное перемещение текущих файлов определяется будущей задачей миграции.

## shadcn/ui, тема и стили

shadcn/ui — исходники компонентов, которыми владеет проект; apps/frontend/packages/ui становится единым владельцем общих компонентов и токенов. Shared UI package вместо отдельных копий в каждом app сохраняет единый вид ценой согласованных изменений общего пакета. Подход соответствует [официальной monorepo-документации](https://ui.shadcn.com/docs/monorepo), исследованной через Context7; она не доказывает работу нашей Module Federation-связки со стилями.

Расположение исходников не задаёт способ runtime-доставки UI. Возможны сборка UI в каждом потребителе или предоставление через Shell; ни один вариант пока не утверждён. При выборе Shell-поставщика надо отдельно решить совместимость версий, недоступность поставщика и самостоятельный запуск remote. Здесь не добавляются shared/exposes/import:false настройки и не обещается отсутствие дублирования JS/CSS. Доступ к публичным exports исходного пакета и предоставление кода в браузере — разные решения.

Shell управляет общей темой страницы, remote использует общие токены и не перезаписывает глобальную тему/стили оболочки. При самостоятельном запуске remote bootstrap обеспечивает ту же базовую тему. Общие reset/base styles подключаются на уровне entry документа, а не внутри каждого UI-компонента; exposed-компонент не должен навязывать повторную глобальную инициализацию. Конкретная сборка component CSS, Tailwind source discovery, порядок слоёв, доставка стилей remote и отсутствие конфликтов в standalone/composition проверяются при внедрении. Наличие общей папки styles само по себе не обеспечивает CSS-изоляцию.

Базовые компоненты, стиль shadcn, палитра, light/dark UX, версии зависимостей, конфигурации Tailwind/components.json и конкретный список устанавливаемых компонентов пока не выбираются: это детали будущей UI-задачи, не препятствующие документированию структуры.

## Результат и проверка

Новая каноническая инженерная страница описывает стандарт с примерами размещения файлов и допустимых/запрещённых зависимостей. Frontend, Tooling, решения, roadmap/open questions, Home и карта источников ссылаются на неё, отделяя будущий стандарт от текущих плоских исходников и отсутствующего UI-пакета. Проверка документационного изменения: согласованность с этим дизайном и обязанностями, локальные ссылки, Prettier затронутого Markdown и git diff. Код, зависимости, настройки, пустые папки и приложения не меняются; build и browser checks не запускаются. Внедрение структуры и UI оформляется отдельно.

В будущей задаче переноса обязательно учесть pnpm discovery вложенных приложений/пакетов, ESLint file globs, относительные TS extends, Vite paths/exposes/env root, scripts и документационные ссылки. Текущие workspace-patterns apps/* и packages/* не следует объявлять достаточными для новой вложенности. Фактические изменения конфигураций, установка shadcn/Tailwind, создание apps/frontend/packages/ui и runtime-проверки выполняются только в отдельной задаче внедрения.

## Уточнения после исследования

По просьбе пользователя изучены первичные источники; его ответ «ок» относится к результатам исследования, последующее полное согласование дизайна v3 и плана v2 записано выше.

- [pnpm packages](https://pnpm.io/settings#packages) поддерживает вложенные расположения через workspace-patterns. Вывод: apps/frontend допустим, но текущие шаблоны надо адаптировать при переносе.
- [Пример Vite Federation](https://github.com/gioboa/react-nx-microfrontend-demo) содержит host/remote и общий shared-ui; его Vite configs объявляют UI shared singleton с обеих сторон. Берётся идея совместимости общего пакета и federation, а не Nx или обещание совместимости всех настроек с нашей версией.
- [shadcn monorepo](https://ui.shadcn.com/docs/monorepo) разделяет общие примитивы и локальные композиции приложений. Наш вложенный путь потребует собственных aliases/components.json.
- [Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md) группирует код по features и предупреждает о barrel-файлах в Vite. В v3 убран обязательный index.ts, публичные границы остаются узкими.
- [Tailwind source detection](https://tailwindcss.com/docs/detecting-classes-in-source-files) требует учитывать источники классов при сборке. Shell не может полагаться на автоматическое обнаружение классов независимо собранного remote. До расширения будущего UI-набора полезно проверить Button и Dialog в standalone и composition, их стили, порталы и тему. В текущем документационном объёме эти проверки не выполняются.
