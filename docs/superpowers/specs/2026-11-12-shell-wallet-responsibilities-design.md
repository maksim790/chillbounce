# Будущие обязанности Shell и Wallet — дизайн v1

Статус: дизайн v1 согласован пользователем ответом «Подтвердить дизайн»; запись согласования 2026-11-12T17:07:43Z. Согласование покрывает этот документ целиком и один [тикет](../../Tasks/document-shell-wallet-responsibilities.md) только на документацию; выполнение отдельно не начато.

## Цель и основания

Определить, какие будущие возможности Chillbounce относятся к Shell и Wallet, чтобы следующие задачи развивали согласованные области. Исходные сценарии — в [продукте](../../01-Product/Overview.md) и [брифе](../../06-Sources/Project-Brief.md); текущая техническая реализация — в [Frontend](../../02-System/Frontend.md). Сейчас есть только оболочка, загрузка remote, обработка ошибок и локальный счётчик; нижеследующие бизнес-возможности ещё не реализованы.

## Рассмотренные подходы и выбор

1. Все пользовательские операции кошелька в Wallet, Shell содержит общую оболочку и доступ. Преимущество: баланс, действие и история принадлежат одному frontend-модулю, без межмодульной координации одного сценария. Цена: Wallet становится функционально шире и потребует внутреннего разделения по сценариям.
2. Wallet содержит балансы/историю, crypto — пополнение, переводы и выводы. Преимущество: меньшие отдельные модули. Цена: один сценарий пересекает два remote; сложнее согласовывать обновления и ошибки. Требований, оправдывающих такое разделение, пока нет.

Пользователь явно выбрал вариант 1 в текущей беседе: «Все операции с кошельком в Wallet; назначение crypto решим позже (рекомендуется)», затем отдельно подтвердил полный дизайн v1. Публичный URL беседы недоступен.

## Предлагаемые обязанности

| Область           | Shell                                                                     | Wallet                                                                            |
| ----------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Общий интерфейс   | Каркас страницы, шапка, меню, навигация между разделами                   | Содержимое раздела кошелька и переходы внутри его сценариев                       |
| Вход и сессия     | Экраны регистрации/входа/выхода, общее состояние входа                    | Использование согласованного контекста доступа; без отдельного входа внутри Shell |
| Доступ к разделам | Отображение доступных разделов по роли, общая реакция на окончание сессии | Отображение доступных действий кошелька и ошибок отказа API                       |
| Активы            | Не хранит и не рассчитывает балансы                                       | Список ETH/тестовых токенов, доступный и зарезервированный баланс                 |
| Пополнение        | Подключает Wallet как раздел                                              | Адрес и инструкции пополнения, отображение статуса зачисления                     |
| Переводы и выводы | Не управляет шагами финансовых сценариев                                  | Формы внутреннего перевода и вывода, результат и статусы                          |
| История           | Не дублирует финансовую историю                                           | История пополнений, переводов, выводов и детали операций                          |
| Ошибки            | Загрузка/недоступность remote при сохранении оболочки                     | Загрузка данных, пустые состояния, ошибки API/валидации в пределах кошелька       |

Это распределение frontend-ответственности. Backend — авторитетный источник пользователей, разрешений, балансов, адресов и статусов операций; он проверяет права и финансовые условия. Клиентские проверки и скрытие кнопок не заменяют backend-проверки. Ledger, ключи, подпись, RPC и reconciliation не принадлежат Shell или Wallet. Новых финансовых правил этим документом не вводится.

## Контракты и ограничения

- Shell подключает Wallet через публичную границу remote, не импортирует его внутренности и не дублирует финансовые данные в общем состоянии.
- Существующий `wallet/Wallet` без props остаётся текущим техническим контрактом. Будущие соглашения о навигации и передаче контекста сессии предстоит определить перед реализацией соответствующих задач; этот документ не утверждает transport, shared store, token storage или router.
- Standalone Wallet остаётся способом локального запуска; отдельный полноценный продукт/вход для него не утверждается.
- При отказе Wallet общая оболочка остаётся доступной; при отказе API состояние финансовой операции нельзя представлять как успешное без подтверждения backend. Точные статусы, идемпотентность, повторные запросы и восстановление определяются в отдельных задачах вместе с backend-контрактом.
- Назначение crypto открыто; ранее упомянутый remote не удаляется из истории планов, но ему не назначаются дублирующие функции. Admin остаётся отдельной будущей областью мониторинга по брифу.
