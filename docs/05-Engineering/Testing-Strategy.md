# Definition of Done и проверки

Предложено Codex при `setup-project init`. Согласовано пользователем ответом «да» 2026-11-12 на предложение файлов и обязательных проверок. Источник согласования: беседа; сводка — [бриф](../06-Sources/Project-Brief.md).

## Обязательные проверки для каждого изменения

- Проверить соответствие согласованным критериям задачи; указать фактические результаты и незакрытые критерии.
- Проверить актуальность затронутой документации, включая различие между требованиями, планами и реализацией.
- Проверить разрешимость локальных Markdown-ссылок. Указать использованный инструмент и результат.

Для текущей инициализации используются read-only validator навыка setup-project и проверка ссылок из корневого AGENTS.md. Validator расположен вне репозитория и не является переносимой зависимостью проекта. В этой среде команда:

```powershell
python -B 'C:\Users\maksimbell\lifetime\codex-workflow\skills\setup-project\scripts\validate-docs.py' --root 'C:\Users\maksimbell\lifetime\projects\chillbounce' --vault docs --format text
```

При недоступности этого инструмента требуется эквивалентная проверка ссылок с явным указанием метода. Команды приложения должны опираться на будущие реальные package scripts и CI-конфигурацию.

## Условные проверки

- Изменения финансовой логики: проверять сбалансированность ledger, защиту от повторной обработки и двойного списания.
- Изменения интеграции с блокчейном: проверять обработку подтверждений и ошибок.

Конкретные тестовые команды и наборы сценариев для этих условий пока недоступны. Их нужно определить при реализации соответствующих механизмов; отсутствие команды не означает успешную проверку.

## Коммиты и интеграция

Перед каждым коммитом форматируйте изменённые в рамках задачи файлы кода через Prettier с конфигурацией репозитория (`pnpm exec prettier <files> --write`), затем выполняйте применимые проверки. Не затрагивайте посторонние файлы. Правило закреплено в [AGENTS.md](../../AGENTS.md).

В последующей беседе пользователь согласовал правила веток, логических коммитов и интеграции, записанные в [AGENTS.md](../../AGENTS.md). По его поручению правила уточнены после проверки неоднозначностей.

- Каждая законченная логическая часть проверяется и коммитится по ходу выполнения тикета, оставляя проект в рабочем состоянии. В группе тикетов используется общая feature-ветка. Обязательные проверки с ошибкой нужно исправить. Если проверка недоступна, коммит разрешён с явным объяснением причины и ограничений; недоступность не считается успешным результатом.
- При содержательных изменениях обновляются затронутые страницы vault. Для чисто механических изменений нужно объяснить, почему обновление vault не требуется.
- Перед интеграцией проверяются полный diff и список коммитов ветки относительно dev. Посторонние изменения нельзя молча включать в интеграцию или удалять.
- После любого merge проверяется итоговое интегрированное состояние до push в dev, даже если конфликтов не было. При конфликтах проверки выполняются также перед созданием merge-коммита. Результат с проваленными обязательными проверками не отправляется; недоступные проверки сопровождаются явным описанием ограничений.
- После завершения, проверки и коммитов самостоятельного тикета выполняются локальный merge в dev, проверка результата и обычный push dev. Для группы merge и push выполняются после всех согласованных дочерних тикетов и общих критериев интеграции; завершение одного дочернего тикета или промежуточный коммит их не запускают. Следующий тикет не выполняется без его выбора пользователем.
- Этот порядок согласован пользователем как стандартный и не требует повторного разрешения на каждый merge/push. PR и push не предлагаются как варианты; PR создаётся только по явному запросу. Явные указания пользователя для конкретной задачи имеют приоритет. После работы сообщаются фактические результаты интеграции и публикации.
- Анализ без изменений не требует пустого коммита, merge или push. При отсутствии либо неоднозначности remote или целевой ветки, расхождении dev, посторонних изменениях или неоднозначных конфликтах сохраняется работа и сообщается препятствие. Автоматический force push, удаление веток и перенос в main не разрешены. При определённом origin и целевой ветке dev разрешён обычный push, создающий remote dev при её отсутствии.
- Исключение для первоначальной настройки: по явному запросу первый коммит проверенных файлов делается в main, после чего от него создаётся dev и выполняется переключение на dev. Отдельная начальная ветка не нужна. Настройка завершается отчётом о проверках и ветках без вариантов интеграции feature-ветки. Дальнейшая разработка следует обычным правилам.

Полные правила main/dev, подготовки и продолжения feature-веток, защиты посторонних изменений и разрешений на интеграцию находятся в AGENTS.md; здесь описана их проверочная часть. Первоначальная настройка отсутствующего Git или dev требует разрешения пользователя; явный запрос на неё уже является разрешением соответствующего объёма и не требует повторного подтверждения. Вызов prepare-task подготавливает тикет; выполнение передаётся start-task.

## Дополнительные проверки

Дополнительные нагрузочные, отказные и эксплуатационные проверки можно предлагать по рискам конкретного изменения. Их состав и пороги пока не согласованы и не являются обязательными gates.

## Недоступные проверки

На момент первоначальной инициализации исходников и инструментов не было. Теперь [package.json](../../package.json) определяет lint, lint:fix, format, format:check и typecheck; установка и описание конфигураций — в [Tooling](Tooling.md), фактические результаты — в [тикете monorepo](../Tasks/initialize-monorepo.md). Для изменений JS/TS/config применяются lint и format:check; при появлении package typecheck scripts применяется их рекурсивный запуск. Пустой typecheck без пакетов не доказывает проверку типов будущих приложений.

По [frontend-тикету](../Tasks/frontend-shell-wallet.md) появились shell/wallet и реальные dev/build/preview/typecheck scripts. Для них применяются lint, format:check, typecheck и build; runtime federation проверяет пользователь в браузере. По его явному решению Playwright и другая тестовая инфраструктура в этом тикете не добавляются и не запускаются. Это исключение не отменяет проверки будущей финансовой или blockchain-логики. CI, API-схем, миграций и backend пока нет; успешные результаты этих областей не заявляются.

Актуальное состояние реализации: [обзор системы](../02-System/Overview.md). Пределы проверенного материала: [карта источников](../06-Sources/Index.md).
